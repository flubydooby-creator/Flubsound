# Requirement Traceability Matrix

This matrix maps every requirement ID from [00 §1](00-understanding-and-plan.md#1-scope-confirmation--requirement-checklist) to the design sections that specify it, the code that implements it, the tests that prove it and its verified status. Status legend: **Implemented and tested** means the requirement is implemented and automated tests assert its core behaviour (any untested sub-part is named in Notes); **Implemented (verified by build / manual run only)** means the code exists, is compiled on CI (for app and plug-in code, see the CI note below) and is exercised headlessly or by hand, but no automated test asserts the requirement's behaviour; **Partially implemented** means only part of the requirement exists or is verified, and Notes say which part. Tests are `TEST_CASE` names from `tests/*.cpp`, all compiled into the `flub_tests` binary, which ctest runs in every CI job that runs tests (`core` on GCC, Clang, MSVC and Apple Clang; `sanitizers` with ASan + UBSan; `rtsan` with the Clang 20 RealtimeSanitizer). `tests/CMakeLists.txt` also compiles the `tools/flubsound-cli` sources except `main.cpp` into `flub_tests`, so the CLI cases in `tests/test_offline_render.cpp` run in every one of those jobs, independent of `FLUB_BUILD_TOOLS`. The exceptions are the RTSan self-test (compiled only with `FLUB_RTSAN`), `tests/test_platform_linux.cpp` (Linux builds only) and the C half of the driver-ABI layout test (skipped on MSVC). The `App:` cases are not in `flub_tests`: they live in `tests/app/*.cpp` and form a second binary, `flub_app_tests`, which compiles the desktop app's own sources (all but `Main.cpp`) with a fake audio device, a fake per-app router and windowless views. It is built only with the app (`FLUB_BUILD_APP=ON`, `FLUB_BUILD_APP_TESTS=ON`), and the CI `app + plugin` job runs it with ctest on windows-2022, macos-14 and ubuntu-24.04. Design links point into `docs/`, `platform/`, `presets/README.md` and the top-level `README.md`; Code paths are relative to the repository root. Figures in Notes say whether a test asserts them, a design doc records them as an author measurement, or a manual or scratch-harness run produced them.

## R1 Real-time audio engine

Interpretations used (from [00 §1](00-understanding-and-plan.md#r1-real-time-audio-engine)):

- **R1.1** is the latency Flubsound **adds** end to end on top of the OS and the application. One budget, with three scope labels (01 §5): **chain** ≈2.1 ms (Low Latency, 100 samples) or 4.0 ms (Balanced, 192) at 48 kHz; **app engine** 3.0 ms (144) or 5.4 ms (260) with the master limiter; **added end-to-end** (estimate, Windows driver path) ≈9.5 ms in Low Latency, the profile that meets ≤ 10 ms, and ≈12–13 ms in Balanced, the upper edge. Today's capture paths add their own buffering (01 §5.3). Quality (≈28 ms chain) is for music and batch use.
- **R1.2** is the JUCE 9 device layer. PipeWire and PulseAudio are reached through the ALSA / JACK compatibility layers for I/O and through `pactl` for routing; a native PipeWire node is roadmap.
- **R1.3**: all DSP is float; metering integrators and long-running accumulators use double where precision matters.
- **R1.4**: every coefficient is derived from the session rate; the chain test covers 11 rates from 8 to 192 kHz.
- **R1.5**: lock-free SPSC FIFOs, no allocation or locks on the audio thread (enforced by tests), drift-compensated resampling between clock domains (`DriftCompensatedFifo` for per-app captures), and denormal protection.

## Known gaps

Every row that is not **Implemented and tested**, with what is missing. Details and figures are in each row's Notes.

- **R1.1 Latency (Partially implemented).** The 10–12 ms end-to-end target is not measured. The ≈9.5 ms and ≈12–13 ms figures are estimates for the Windows virtual-driver path, which is design only; there is no loopback measurement (07 item 1.2, 10 §5 test 8), and the UI readout is reported, not measured. Today's Windows process-loopback path alone adds a 612-frame (12.75 ms) FIFO target, and the default Linux PipeWire quantum is ≈21 ms unless forced to 256 (01 §5.3). The docs now share one budget with explicit scopes (01 §5).
- **R1.2 Audio backends (Partially implemented).** No test opens a device. CI run 36247109446 built the app and plug-in on Windows (WASAPI), macOS (CoreAudio) and Linux (ALSA / JACK); ASIO has no recorded build (it needs the Steinberg SDK). The native PipeWire `pw_filter` node, per-stream `node.latency`, the exclusive-mode policy (08 D2) and the ASIO single-client note (08 D10) are roadmap, and no device-lab results exist.
- **R1.5 Buffer management (Partially implemented).** Glitch-free operation on the real audio thread is not exercised: the app's callback code is not RTSan-annotated (it is allocation-, free- and, on Linux, lock-tested with a fake device in `flub_app_tests`, not yet on CI), module `reset()` and setters are not RTSan-annotated, and `DriftCompensatedFifo` is proven in simulation only. Missing: real-device soak and glitch detector (07 items 1.1, 1.10), CPU-overload watchdog, crossfaded engine swap on structural changes, RealtimeKit, driver clock slaving (design only) and FIFO `Stats` in the UI.
- **R3.5 Anti-clipping + THD protection (Partially implemented).** THD protection is a proxy (clip energy at the maximizer clipper) that covers only governed macro contributions, not base `max.drive` / `sat.drive` or saturator THD. The governor's clip-energy branch is now tested as a unit and end to end through the chain (`tests/test_protection_gaps.cpp`, not yet run on CI); the proxy and its coverage are what remain.
- **R4.1 Dark GUI (verified by build / manual run only).** No tests of the look or layout (`flub_app_tests` checks only the meter views' values, R4.2); screenshots are uploaded, not diffed; Windows and macOS rendering are unverified (CI builds the app there but renders nothing). Screen-reader live values, UI scale and high-contrast theme (roadmap 3.6), onboarding (1.6 / 3.6), localisation (3.7) and the dark plug-in editor (2.9) are missing.
- **R4.4 Tray + global hotkeys (Partially implemented).** Linux global hotkeys are implemented for X11 (`XGrabKey`) and tested under Xvfb (locally, and by the CI `sanitizers` job's Xvfb step, first green in run [36269443100](https://github.com/flubydooby-creator/Flubsound/actions/runs/36269443100) on commit `df28c48`, where the X11 case ran rather than skipped). Wayland sessions now use the xdg-desktop-portal GlobalShortcuts interface, tested only against a mock portal on a private `dbus-daemon` (not yet on CI, never on a real desktop); shortcuts the user declines are only logged to stderr. Start with the OS now exists on all three OSes, but only the Linux XDG autostart entry is tested; the Windows `Run`-key code has only been compiled (MinGW) and the macOS `SMAppService` code has been neither built against a real SDK nor run. The tray on every OS and Windows / macOS hotkeys are build-verified only with no recorded manual verification.
- **R4.5 Per-app profiles and routing (Partially implemented).** macOS is unsupported (process taps, roadmap 3.2). Windows programmatic endpoint moves exist only in opt-in `FLUB_ENABLE_UNDOCUMENTED_ROUTING` builds, are not validated per Windows build (07 item 2.4) and need the unbuilt virtual driver. RoutingPanel and all Windows routing / capture code are untested (`AppRouting` itself is tested with a fake router and fake captures, not yet on CI); Linux moves are not run in CI. Automatic profile switching by foreground game is roadmap 2.5.
- **R4.6 Virtual device / cable (Partially implemented).** No virtual driver exists: the Windows WaveRT driver (only its ABI header exists), the macOS Audio Server Plug-in and the native PipeWire node are designed only (roadmap 2.1–2.3, 3.1, 3.5). On Linux, connecting sink monitors to the device input is not automated and multi-strip mapping has no UI. The Linux sinks, PipeWire drop-ins and cable detection are untested.
- **R5.3 Neural readiness (Partially implemented).** The extension points exist and are tested, but everything neural is designed only: no `core/include/flub/neural/`, ONNX Runtime, inference worker, deadline-miss fallback, model manifest or model. Adding a module needs a code change (fixed slot array), and the profile eligibility rule is not enforced in code.
- **R6.1 Turtle Beach headsets (Partially implemented).** Every device profile is `labVerified:false`; the device-lab plan (10 §5, 07 item 1.10) has not been run on a real headset. The Linux transport query returns Unknown; the app applying the cap on a device change is now tested headlessly (`flub_app_tests`, not yet on CI), but the banner and preferred-output behaviour are untested; the master limiter at −2 / −3 dBTP and the air-exciter cut-off are now tested directly (not yet on CI); Game / Chat virtual-endpoint routing needs the unbuilt drivers; the headset microphone is not processed.

Rows marked Implemented and tested can still name untested sub-parts in their Notes: notably R2.8 (the Music mode bands are not asserted), R2.9 (Gaming Boost staging and real-game efficacy), R2.10 (match accuracy only where the ceiling cap is not involved; the ModuleSlot test does not prove a smooth crossfade between differing paths), R3.1 (the true-peak bound is measured, not proven), R3.2 (AutoLevel convergence to its target), R4.2 (painting and layout, the IEC deflection scale, peak hold and the `LoudnessPanel` momentary / integrated / LRA / true-peak readouts; its `flub_app_tests` cases have not run on CI yet), R5.1 (progress output and command-line parsing into `batch`) and R5.2 (the desktop app cannot export; WAV only, always stereo; the static ceiling trim and the DAW-bounce route are untested). Closed in this pass, by tests green on CI in run 9: the LoudnessMatch unit tests (R2.1), the Width and Clarity macros (R2.8), A/B and bypass click-freedom (R2.10) and the CLI loudness-target loop (R3.2, R5.1). The documentation inconsistencies an earlier pass recorded are fixed: the Windows driver README §6 master-limiter count and its ≤ 15 ms goal (it now uses the single budget of 01 §5), the missing R4.6 row in 06 §14, the 03 §0.1 double-precision list, the stale 08 D1 note on drift tests, and the stale comment in the CD-band limiter test.
